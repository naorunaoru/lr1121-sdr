# 250 kHz frequency-playback tests

Measured 2026-10-23 on Core1121-HF, transceiver 1.3 and RP2040. Carrier 868.350 MHz, requested HP power −9 dBm, physical SPI 15.625 MHz. The Flipper used the existing fast asynchronous recorder with frequency-offset compensation disabled. No SPI overclock or queue enlargement was required.

## Result

250 kHz passed the waveform-delivery checks. Three streamed runs of 3,002,368 updates (12.009472 s nominal each) completed with correct full checksums, final indices, bank sequencing and retained source/frequency-register readbacks. Two included a 40 ms host pause. All had zero player underruns and zero USB-starved polls. The stream preserves waveform entries; this does **not** establish a uniformly spaced 4 µs update grid.

| Streamed 250 kHz run | Host pause | Minimum refill margin | Maximum bank write | Minimum queued banks |
| --- | ---: | ---: | ---: | ---: |
| tx-250000-long-1 | 0 ms | 1.948 ms | 5.545 ms | 7 |
| tx-250000-long-2 | 40 ms | 1.976 ms | 5.584 ms | 3 |
| tx-250000-long-3 | 40 ms | 1.916 ms | 5.572 ms | 3 |

A bank contains 2,048 updates: 8.192 ms at 250 kHz. The matched short 200 kHz stream had a 5.100 ms minimum margin and 4.703 ms maximum bank write; the short 250 kHz stream had 2.112 ms and 5.438 ms respectively. The higher interrupt load increases refill cost as well as shortening the available window.

## Timing and what remains unresolved

Both preloaded and streamed 250 kHz playback show late timer servicing. In the short preloaded RF case, 85 of 128 retained **diagnostic** records had the next timer interrupt pending before return, versus zero at 200 kHz. Those samples are deliberately concentrated on the three diagnostic updates per bank and are not a random sample of ordinary updates. The logging bracket is 123–126 clocks in that control and excludes entry/return work; it already leaves insufficient headroom inside a 128-clock period.

The foreground observer caught an ordinary preloaded interruption of 90 clocks (2.8125 µs), but missed the slower logging chains. Streamed maxima reached 27.688 µs spanning seven timer interrupts plus native SPI work; that is not the duration of one ISR. A timer-only control caught no IRQ-containing foreground window, so its complete-interruption maximum is unavailable. Modulo phase brackets and the software IRQ epoch cannot prove that timer expiries never coalesce.

Long controls remove SPI during playback and improve the RTC endpoint resolution:

| Case, 3,002,368 updates | Requested rate | Mean against nominal 32,768 Hz RTC | RTC ticks |
| --- | ---: | ---: | ---: |
| tx-200000-preloaded-long | 200000 | 199974.037937 updates/s | 491972 |
| tx-250000-preloaded-long-1 | 250000 | 249967.293375 updates/s | 393578 |
| tx-250000-preloaded-long-2 | 250000 | 249967.928492 updates/s | 393577 |
| tx-250000-long-1 | 250000 | 249965.388045 updates/s | 393581 |
| tx-250000-long-2 | 250000 | 249965.388045 updates/s | 393581 |
| tx-250000-long-3 | 250000 | 249964.752941 updates/s | 393582 |

The long preloaded 250 kHz controls took 393577–393578 RTC ticks; the streamed runs took 393581–393582. Streaming therefore adds about 92–153 µs over 12 seconds (roughly 23–38 nominal update periods). This exceeds one RTC tick, but the controls were not simultaneous and oscillator drift is not excluded. The result is consistent with occasional coalesced timer deadlines under SPI load; it does not identify their exact locations. All source entries still reached the frequency register in sequence according to the checksum, bank sequencing and sparse readbacks.

Rates use `(count + 1) * 32768 / (rtc_done - rtc_start)`: completion is recorded in the interrupt after the last update. The RTC is not an external calibrated reference. Compare the controls before interpreting the offset from the nominal update rate. Checksums establish delivered values, not timer-deadline compliance.

## External observation

All seven RF captures reported zero recorder drops and no I/O error. In the trimmed active windows all pulse-pair periods passed the existing broad ±20% tone-frequency check. With the previously measured 1 µs-per-cycle recorder correction, the 250 kHz cases gave a median 1886.792 Hz for the nominal 1892.090 Hz reference; the 200 kHz controls gave 1510.574 Hz for 1513.672 Hz. This supports gross RF continuity only. The binary Flipper capture cannot establish frequency-update jitter, audio fidelity, occupied bandwidth or spectral purity.

## Reproduction and compatibility

Use [the TX build/install procedure](tx.md), including the new player and Pico firmware. The 4076-byte player hash is `28bb16f1ef837bc71fb71d38f817ba1be2e66bd20166c0d0a450045b9f8ad1e3`; Pico is `1.0.8-txopt4`. ABI `0x46535433` prevents mixing with the older player that rejects periods below 160 clocks. The new minimum is 128 clocks. Default rate remains 200 kHz. ISR, SPI speed, queue size and diagnostic cadence otherwise remain unchanged.

```sh
python host/tx.py tone build/tone250.s16be --rate 250000 --frequency 1892.08984375
python host/tx.py play build/tone250.s16be --rate 250000 --repeat 733 \
  --tag-blocks --timeout-ms 12809 --out build/tx250-long
```

For the preloaded timing control omit `--tag-blocks` and add `--preloaded`. For the host-pause case add `--pause-block 400 --pause-ms 40`. Output directories must be new. Both the native TX timeout and independent Pico reset deadline remain enabled.

All 12 cases completed; 21,626,880 verified updates, including standby controls. Native and Python checks passed (36 Python tests); both changed firmware components built. Each campaign restored the ordinary Pico 1.0.8 and receiver extension, with LR1121 1.3 in standby and error flags zero. Flipper was left idle. No bootloader update was performed.

Raw captures, device-bound images and serial logs remain in ignored build directories. The repository contains the [sanitized measurements](measurements/tx-250k.json). This establishes 250 kHz as a tested streaming rate, not the absolute hardware upper limit.
